## Push vs polling

The Qubic network produces a new tick roughly every second. You have two options for tracking ticks:

**Polling** — call `live.getTickInfo()` on a timer:
- Simple to implement
- One HTTP round-trip per poll cycle
- You may miss ticks between polls or poll more often than needed

**Push** — subscribe via Bob's WebSocket:
- Single connection, zero per-tick overhead
- Every tick is delivered as it happens
- Requires connection lifecycle management

Bob implements the push model. Once subscribed, events arrive as async iterator values without any polling.

## The AsyncIterable model

Every subscription method returns an `AsyncIterable<SubscriptionEvent<T>>`. Consume it with `for await...of`:

```ts
for await (const event of bob.subscription.subscribeNewTicks()) {
  console.log(event.data.tick, event.isCatchUp)
}
```

Each `SubscriptionEvent<T>` has two fields:

| Field | Type | Description |
|---|---|---|
| `data` | `T` | The payload for this event |
| `isCatchUp` | `boolean` | `true` for buffered events replayed after a reconnect |

The four subscription methods:

| Method | Data type | Description |
|---|---|---|
| `subscribeNewTicks(options?)` | `BobTickNotification` | `tick` and `epoch` for every new tick |
| `subscribeTickStream(options?)` | `BobIndexedTick` | Full tick data including transaction hashes |
| `subscribeLogs(filter?, options?)` | `BobLogEvent` | Contract event logs matching an optional filter |
| `subscribeTransfers(filter?, options?)` | `BobTransferEvent` | QU transfers matching an optional filter |

## Reconnection

Bob reconnects automatically after a connection drop with exponential backoff. The `for await...of` loop pauses during reconnection and resumes once the connection is restored — you do not need to restart the loop.

Use the `onReconnect` callback on `createBobSubscriptionClient` (or the `subscription` sub-client options) to observe reconnect attempts:

```ts
import { createBobClient } from "@qubic.org/bob"

const bob = createBobClient({
  subscription: {
    autoReconnect: true,
    maxReconnects: 10,
    onReconnect: (attempt) => console.log("Reconnecting, attempt", attempt),
  },
})
```

## Catch-up buffering

After a reconnect, the server sends buffered events that arrived during the disconnection window. The `isCatchUp` flag on each `SubscriptionEvent` identifies these:

```ts
for await (const event of bob.subscription.subscribeNewTicks()) {
  if (event.isCatchUp) {
    // This tick arrived during a connection gap
    // Useful for backfilling state, but skip if you only care about live ticks
    continue
  }
  // Live tick — process normally
  updateDisplay(event.data)
}
```

Catch-up events arrive in order, before any live events. Once `isCatchUp` becomes `false`, the subscription is caught up to the live tip.

## Cancellation

Pass an `AbortSignal` to stop an individual subscription without closing all subscriptions:

```ts
const controller = new AbortController()

for await (const event of bob.subscription.subscribeNewTicks({ signal: controller.signal })) {
  if (shouldStop) controller.abort()
  processEvent(event)
}
```

---

## Stopping all subscriptions

`bob.subscription.close()` closes the WebSocket and ends all active `for await...of` loops:

```ts
process.on("SIGINT", () => {
  bob.subscription.close()
  process.exit(0)
})
```

## Connection status

`bob.subscription.connectionStatus` is a `ReadableStream<'connected' | 'disconnected' | 'reconnecting'>` that tracks the WebSocket lifecycle:

```ts
const reader = bob.subscription.connectionStatus.getReader()
while (true) {
  const { done, value } = await reader.read()
  if (done) break
  console.log("WebSocket status:", value)
}
```

The stream closes when `bob.subscription.close()` is called.
